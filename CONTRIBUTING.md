# Contributing to Security Triage Agent

Contributions are welcome. The project’s value comes from preserving clear authority boundaries,
not from maximizing model autonomy.

## Before proposing a change

- Read the [architecture](docs/architecture.md), [security invariants](docs/security-invariants.md),
  and [threat model](docs/threat-model.md).
- Use synthetic data only. Do not submit credentials, real alerts, customer or employer data,
  infrastructure identifiers, or provider payloads.
- Discuss new trust boundaries, provider adapters, actions, or schema changes before implementation.

## Non-negotiable boundaries

- Models never receive provider credentials or invoke application tools directly.
- Every evidence request crosses `ToolGateway` authorization and scope checks.
- Canonical invocation and action IDs are generated by application code.
- Evidence provenance and strict schemas are enforced at trust boundaries.
- Deterministic policy remains authoritative after model output is parsed.
- AI cannot approve an action; high-impact actions require recorded human approval.
- Real provider writes are prohibited until explicitly designed and reviewed.
- Private chain-of-thought is never requested or persisted.
- Validation, policy, authorization, and audit failures fail closed.

## Development workflow

Follow the [development guide](docs/development.md). Keep patches focused, add tests for behavior
changes and negative/security cases, and run:

```bash
make check
```

Run `make release-smoke` for packaging/install changes and `make container-smoke` for Docker or
deployment changes. Do not weaken assertions to make a failure pass.

## Pull requests

Explain the problem, trust-boundary impact, tests actually run, documentation changes, and any
remaining risk. Link an issue when one exists. By intentionally submitting a contribution for
inclusion, you agree that it is submitted under the repository’s Apache License 2.0 terms, as
described by Section 5 of that license. Ensure you have the right to contribute the work.

Security vulnerabilities belong in the private process described by [SECURITY.md](SECURITY.md),
not a public issue.
